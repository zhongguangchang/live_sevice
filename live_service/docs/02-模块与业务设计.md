# 生活服务网 · 模块与业务设计

## 一、整体分层结构

沿用原项目的 Maven 三模块结构，不推倒重来。这套分层对毕业设计来说
已经足够规范，改成微服务反而会让工作量失控。

```
live_service
├── sky-common          公共模块（无业务，谁都能依赖）
│   ├── constant        常量：Result 状态、Redis key、MQ 队列名、状态枚举、提示语
│   ├── context         BaseContext：基于 ThreadLocal 存放当前登录用户 id
│   ├── enumeration     枚举
│   ├── exception       业务异常体系
│   ├── json            JacksonObjectMapper：HTTP 接口的日期格式
│   ├── properties      配置类：JWT、阿里云 OSS、微信支付
│   ├── result          Result / PageResult：统一返回体
│   └── utils           JwtUtil、AliOssUtil、WeChatPayUtil、HttpClientUtil
│
├── sky-pojo            数据模型模块（只有 POJO，没有任何逻辑）
│   ├── entity          数据库实体，与表一一对应
│   ├── dto             接收前端入参
│   └── vo              返回给前端的视图对象
│
└── sky-server          服务模块（所有业务逻辑）
    ├── config          配置类
    ├── interceptor     拦截器（管理端/用户端双 JWT 校验）
    ├── handler         GlobalExceptionHandler 全局异常处理
    ├── annotation      自定义注解（@AutoFill 自动填充、@RateLimit 限流）
    ├── aspect          AOP 切面（自动填充、限流）
    ├── controller
    │   ├── admin       管理端接口/  admin
    │   └── user        用户端接口  /user
    ├── service         业务接口
    │   └── impl        业务实现
    ├── mapper          MyBatis Mapper 接口
    ├── mq
    │   ├── producer    消息生产者
    │   └── consumer    消息消费者
    ├── websocket       订单状态实时推送
    ├── task            定时任务（兜底对账）
    └── resources
        ├── mapper      MyBatis XML
        └── lua         Redis Lua 脚本
```

**接口路径约定**（沿用原项目，前端不用改）：

- 管理端：`/admin/**`，请求头 `token`
- 用户端：`/user/**`，请求头 `authentication`

## 二、业务模块划分

共 9 个模块。每个模块都对应一组 Controller + Service + Mapper。

### 模块 1 · 认证权限

**职责**：管理端登录、用户端微信登录、Token 校验、角色鉴权。

| 做什么 | 涉及的原项目类 |
|---|---|
| 管理端账号密码登录，签发 JWT | EmployeeController、EmployeeService |
| 用户端微信 code 换 openid，自动注册 | UserController、UserService |
| 双拦截器分别校验两端 Token | JwtTokenAdminInterceptor、JwtTokenUserInterceptor |
| **新增**：按 role 做接口级鉴权 | 新增注解 + 切面 |

### 模块 2 · 服务商品

**职责**：服务分类、服务项目、服务规格、服务套餐的增删改查与上下架。

| 做什么 | 对应改造 |
|---|---|
| 分类管理 | CategoryController（改） |
| 服务项目 CRUD、起售停售、图片上传 | DishController → ServiceItemController |
| 服务规格管理 | 并入服务项目编辑 |
| 服务套餐 CRUD | SetmealController → ServicePackageController |
| **新增**：服务项目详情页含评价列表 | 新增接口 |

**关键业务规则**（沿用原项目思路，改语义）：

- 起售中的服务项目不能删除
- 被套餐引用的服务项目不能删除（反查 `service_package_item`）
- 分类下有服务项目或套餐时不能删除
- 套餐内服务项目已停售时，套餐不能启用

### 模块 3 · 服务人员（师傅）

**职责**：师傅档案、技能配置、接单状态管理、派单。

| 做什么 | 说明 |
|---|---|
| 师傅档案 CRUD | 新增 |
| 师傅技能配置 | 新增，多对多 |
| 师傅接单状态切换 | 可接单 / 忙碌 / 休息中 |
| **派单** | 新增，本项目重点 |
| 师傅端：查看我的订单、接单、拒单、开始服务、完成服务 | 新增 |

**派单算法**（初版，够用且有讲头）：

```
输入：订单（含 serviceId）
  1. 查 serviceId 所属 categoryId
  2. 从 provider_skill 找出掌握该分类的师傅    ← 技能过滤
  3. 过滤掉 status != 可接单 的师傅            ← 状态过滤
  4. 过滤掉该时段已有订单、档期冲突的师傅        ← 档期过滤（查 slot）
  5. 剩下的按 score 降序、order_count 升序排序  ← 评分优先、负担均衡
  6. 取第一个派单，发 5 分钟延迟消息
  7. 5 分钟未接单 → 转派下一个
```

### 模块 5 · 订单交易

## 三、核心业务流程

### 流程 1 · 浏览与下单（主流程）

```
小程序首页
   │  GET /user/category/list           加载服务分类
   │  GET /user/service/list?categoryId 加载服务列表（走 Redis 缓存）
   ▼
服务详情页
   │  GET /user/service/{id}            服务详情 + 规格 + 评价
   │  GET /user/slot/available          查该服务某天的可预约时段
   ▼
加入服务清单
   │  POST /user/shoppingCart/add       选规格（带价差）
   ▼
提交订单
   │  ① 校验服务区域（district_code 是否在 service_area）
   │  ② 校验时段有效性
   │  ③ 【Redis】Lua 脚本原子预扣名额  ← 核心
   │  ④ 落库：service_order + service_order_item
   │  ⑤ 【MQ】发 15 分钟延迟消息        ← 核心
   ▼
微信支付
   │  PUT /user/order/payment
   ▼
支付回调 /user/notify/paySuccess
   │  ① 分布式锁 + 订单号唯一索引保证幂等
   │  ② 【MySQL】乐观锁扣减 booked_count
   │  ③ 订单状态 → 待接单
   │  ④ 【MQ】发服务前 1 小时提醒消息
   ▼
等待派单
```

### 流程 2 · 派单与服务

```
管理端看到「待接单」订单
   │  PUT /admin/order/dispatch   派单
   │  派单算法：技能过滤 → 状态过滤 → 档期过滤 → 评分排序
   ▼
【MQ】发 5 分钟接单超时消息
   │
   ├── 师傅接单 PUT /provider/order/accept
   │      │  订单状态 → 已接单
   │      │  WebSocket 推送给管理端
   │      │  【MQ】服务前 1 小时提醒用户和师傅
   │      ▼
   │   师傅上门 → 开始服务 → 订单状态 → 服务中
   │      ▼
   │   服务完成 → 订单状态 → 待评价
   │      │  【MQ】发 7 天自动好评消息
   │      │  更新师傅 order_count
   │      ▼
   │   用户评价 → 订单状态 → 已完成
   │
   └── 5 分钟未接单
          │  自动转派给下一个师傅（回到派单步骤）
```

### 流程 3 · 订单超时取消（MQ 延迟队列主场景）

```
提交订单时
   └── 发消息到 life.order.delay.exchange
          │
          ▼
      life.order.delay.queue（没有消费者，消息在这里干等 15 分钟）
          │
          │ TTL 到期，成为死信
          ▼
      life.order.dlx.exchange
          │
          ▼
      life.order.timeout.queue
          │
          ▼
      OrderTimeoutConsumer 消费
          │
          ├─ 幂等检查：先查订单，只有仍为「待付款」才继续
          │   （RabbitMQ 是至少一次投递，消息可能重复到达）
          │
          ├─ 已支付 → 直接跳过
          │
          └─ 仍待付款
                 ├── 订单状态 → 已取消，原因「超时未支付」
                 ├── 【Redis】Lua 脚本回补名额（幂等）
                 └── WebSocket 通知管理端
```

**这套设计替代了原项目的 `OrderTask.processTimeoutOrder()`**，
对比一下差别就明白为什么值得改：

| | 原定时任务方案 | MQ 延迟队列方案 |
|---|---|---|
| 触发精度 | 最坏差 1 分钟（每分钟扫一次） | 精确到毫秒 |
| 数据库压力 | 每分钟一次全表扫描，订单越多越慢 | 零空转，只在有订单时产生负载 |
| 失败处理 | 只能等下一轮扫描 | 失败自动重试 3 次 |
| 扩展性 | 多实例部署会重复执行（需要分布式锁） | 天然支持多实例竞争消费 |

**但 `OrderTask` 不要删**，把它降级成兜底对账任务。
理由是 MQ 不是 100% 可靠——可能丢消息、消费者可能挂、
Redis 可能挂了之后重启丢数据。保留定时对账是工程上负责任的做法，
答辩时主动说出这一点，比只说「我用了 MQ」有说服力得多。

### 流程 4 · 评价与评分回写

```
订单状态 → 待评价
   │
   ├── 用户提交评价
   │      │  三维打分 + 图文
   │      │  【MQ】异步回写评分
   │      ▼
   │   ReviewConsumer 消费
   │      ├── 更新 provider.score / good_rate
   │   └── 更新 service_item.score
   │      │
   │      ▼
   │   订单状态 → 已完成
   │
   └── 7 天未评价（MQ 延迟队列触发）
          │  自动标记已完成，默认好评
          └─ 避免订单永远挂在「待评价」，统计口径才好算
```

### 流程 5 · 兜底对账

```
OrderTask（每 5 分钟）
   │
   ├── 1. 扫 Redis 与 MySQL 的名额差异
   │      对每个 slot：Redis 剩余 + 已预约数  vs  total_stock - booked_count
   │      不一致 → 以 MySQL 为准，重写 Redis
   │
   ├── 2. 扫「待付款但已超过 20 分钟」的订单
   │      （兜底 MQ 丢消息的情况）
   │      → 关单 + 回补名额
   │
   └── 3. 扫「待评价超过 7 天」的订单
          → 自动完成
```

## 四、技术亮点设计

### 亮点 1 · Redis 原子预扣防超卖

**问题**：周末 9:00-11:00 的深度保洁只有 3 个师傅能接。
100 个人同时抢，如果用数据库行锁，请求会串行化，吞吐上不去；
如果先查再扣，两步之间有竞态窗口，必然超卖。

**方案**：把「校验名额 → 扣减 → 记录用户」三步写进一个 Lua 脚本。
Redis 单线程执行脚本，期间不会插入其他命令，天然原子。

脚本见 `sky-server/src/main/resources/lua/slot_deduct.lua`，
返回值约定：`>=0` 成功、`-1` 未预热、`-2` 已约满、`-3` 重复预约。

**关键细节**：执行 Lua 必须用 `StringRedisTemplate`。
如果用了配 JSON 序列化器的 `RedisTemplate`，Lua 里 `tonumber()`
拿到的会是带引号的字符串，直接报错。这个坑很多人踩。

**名额回补的幂等**：`slot_rollback.lua` 用 `SREM` 的返回值做判断——
返回 1 说明确实移除了（第一次回补），返回 0 说明已经回补过。
没有这道判断的话，订单取消接口被重复调用会把名额越加越多。

### 亮点 2 · Redis 与 MySQL 双层库存 + 定时对账

单靠 Redis 不安全（Redis 可能挂、可能丢数据），
单靠 MySQL 性能不够。所以做成两层：

| 时机 | 操作 |
|---|---|
| 下单 | Redis 预扣（快，抗并发） |
| 支付成功 | MySQL 乐观锁落账（准，作最终事实） |
| 取消 / 超时 | Redis 回补 + MySQL 释放 |
| 每 5 分钟 | 定时对账，以 MySQL 为准修正 Redis |

这就是 CAP 里的最终一致性实践，也是答辩能讲深度的点。

### 亮点 3 · MQ 延迟队列的四种业务落地

同一套 TTL + 死信队列机制，复用在四个场景：

| 场景 | 延迟 | 类型 |
|---|---|---|
| 订单超时取消 | 15 分钟 | 固定延迟 |
| 服务前 1 小时提醒 | 视预约时间而定 | 不定延迟 |
| 完成后 7 天自动好评 | 7 天 | 固定延迟 |
| 派单后 5 分钟未接单转派 | 5 分钟 | 固定延迟 |

**TTL 队列化实现要点**：声明一个没有消费者的队列，
消息在里面等 TTL 到期变成死信，被死信交换机转发到真正被监听的队列。

**要主动说明的已知问题**：不定延迟场景会有「队头阻塞」——
队列里的消息是先进先出排队过期的，只有队头过期了才会检查下一条。
如果队头是一条 TTL 23 小时的消息，后面 TTL 1 小时的消息也得等。
解决方案是装 `rabbitmq_delayed_message_exchange` 插件（内部用时间轮），
或拆成多个固定档位的队列。

**消息可靠性三件套**：

1. 生产者确认（`publisher-confirm-type: correlated`）—— 消息没到交换机时能感知
2. 生产者退回（`publisher-returns: true`）—— 路由不到队列时能感知
3. 消费者手动 ACK（`acknowledge-mode: manual`）—— 处理成功才确认

### 亮点 4 · 缓存三兄弟

原项目除了一个 `SHOP_STATUS` 之外几乎没用缓存。补上之后：

| 问题 | 场景 | 方案 |
|---|---|---|
| 穿透 | 有人拿不存在的服务 id 反复请求 | 缓存空值 + 布隆过滤器预热服务 id |
| 击穿 | 热门服务缓存刚好过期，瞬间大量请求打到数据库 | 互斥锁重建 / 逻辑过期 |
| 雪崩 | 大批服务缓存设置了同样的过期时间，同时失效 | 随机 TTL（基础值 + 随机偏移） |

### 亮点 5 · 限流与防刷

自定义 `@RateLimit` 注解 + AOP 切面，用 Redis 计数器实现。
加在下单、支付、评价这类写接口上，防止用户连点或脚本刷单。

### 亮点 6 · 订单状态实时推送

复用原项目已有的 WebSocket。订单支付成功、师傅接单、
服务完成时推送给管理端页面，替代轮询。
