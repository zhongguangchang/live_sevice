# 生活服务网 · 模块与业务设计

## 一、整体分层结构

沿用原项目的 Maven 三模块结构，不推倒重来。这套分层对毕业设计来说
已经足够规范，改成微服务反而会让工作量失控。

```
live_service
├── sky-common          公共模块（无业务，谁都能依赖）
│   ├── constant        常量：Result 状态、Redis key、MQ 队列名、状态枚举、提示语
│   ├── context         BaseContext：基于 ThreadLocal 存放当前登录用户 id
│   ├── enumeration     枚举
│   ├── exception       业务异常体系
│   ├── json            JacksonObjectMapper：HTTP 接口的日期格式
│   ├── properties      配置类：JWT、阿里云 OSS、微信支付
│   ├── result          Result / PageResult：统一返回体
│   └── utils           JwtUtil、AliOssUtil、WeChatPayUtil、HttpClientUtil
│
├── sky-pojo            数据模型模块（只有 POJO，没有任何逻辑）
│   ├── entity          数据库实体，与表一一对应
│   ├── dto             接收前端入参
│   └── vo              返回给前端的视图对象
│
└── sky-server          服务模块（所有业务逻辑）
    ├── config          配置类
    ├── interceptor     拦截器（管理端/用户端双 JWT 校验）
    ├── handler         GlobalExceptionHandler 全局异常处理
    ├── annotation      自定义注解（@AutoFill 自动填充、@RateLimit 限流）
    ├── aspect          AOP 切面（自动填充、限流）
    ├── controller
    │   ├── admin       管理端接口/  admin
    │   └── user        用户端接口  /user
    ├── service         业务接口
    │   └── impl        业务实现
    ├── mapper          MyBatis Mapper 接口
    ├── mq
    │   ├── producer    消息生产者
    │   └── consumer    消息消费者
    ├── websocket       订单状态实时推送
    ├── task            定时任务（兜底对账）
    └── resources
        ├── mapper      MyBatis XML
        └── lua         Redis Lua 脚本
```

**接口路径约定**（沿用原项目，前端不用改）：

- 管理端：`/admin/**`，请求头 `token`
- 用户端：`/user/**`，请求头 `authentication`

## 二、业务模块划分

共 9 个模块。每个模块都对应一组 Controller + Service + Mapper。

### 模块 1 · 认证权限

**职责**：管理端登录、用户端微信登录、Token 校验、角色鉴权。

| 做什么 | 涉及的原项目类 |
|---|---|
| 管理端账号密码登录，签发 JWT | EmployeeController、EmployeeService |
| 用户端微信 code 换 openid，自动注册 | UserController、UserService |
| 双拦截器分别校验两端 Token | JwtTokenAdminInterceptor、JwtTokenUserInterceptor |
| **新增**：按 role 做接口级鉴权 | 新增注解 + 切面 |

### 模块 2 · 服务商品

**职责**：服务分类、服务项目、服务规格、服务套餐的增删改查与上下架。

| 做什么 | 对应改造 |
|---|---|
| 分类管理 | CategoryController（改） |
| 服务项目 CRUD、起售停售、图片上传 | DishController → ServiceItemController |
| 服务规格管理 | 并入服务项目编辑 |
| 服务套餐 CRUD | SetmealController → ServicePackageController |
| **新增**：服务项目详情页含评价列表 | 新增接口 |

**关键业务规则**（沿用原项目思路，改语义）：

- 起售中的服务项目不能删除
- 被套餐引用的服务项目不能删除（反查 `service_package_item`）
- 分类下有服务项目或套餐时不能删除
- 套餐内服务项目已停售时，套餐不能启用

### 模块 3 · 服务人员（师傅）

**职责**：师傅档案、技能配置、接单状态管理、派单。

| 做什么 | 说明 |
|---|---|
| 师傅档案 CRUD | 新增 |
| 师傅技能配置 | 新增，多对多 |
| 师傅接单状态切换 | 可接单 / 忙碌 / 休息中 |
| **派单** | 新增，本项目重点 |
| 师傅端：查看我的订单、接单、拒单、开始服务、完成服务 | 新增 |

**派单算法**（初版，够用且有讲头）：

```
输入：订单（含 serviceId）
  1. 查 serviceId 所属 categoryId
  2. 从 provider_skill 找出掌握该分类的师傅    ← 技能过滤
  3. 过滤掉 status != 可接单 的师傅            ← 状态过滤
  4. 过滤掉该时段已有订单、档期冲突的师傅        ← 档期过滤（查 slot）
  5. 剩下的按 score 降序、order_count 升序排序  ← 评分优先、负担均衡
  6. 取第一个派单，发 5 分钟延迟消息
  7. 5 分钟未接单 → 转派下一个
```

### 模块 4 · 排期时段

**职责**：师傅档期生成、时段名额管理、Redis 名额预扣。Redis 亮点的落点。

| 做什么 | 说明 |

| 查询某服务某天的可预约时段 | 用户端下单页用 |
| **名额预扣** | Lua 脚本原子扣减 Redis |
| **名额回补** | Lua 脚本幂等回补 |
| **缓存预热** | 时段开售前把库存写入 Redis |
| **对账兜底** | 定时任务比对 Redis 与 MySQL |

### 模块 5 · 订单交易

**职责**：下单、支付、取消、派单、接单、服务、完成。整个系统的主动脉。

| 做什么 | 说明 |
|---|---|
| 提交订单 | Redis 预扣 → 落库 → 发超时延迟消息 |
| 订单支付 | 微信支付 / 模拟支付 |
| 支付回调 | 幂等处理，MySQL 落账，发服务提醒消息 |
| 用户取消 | 关单 + 回补名额 |
| 超时取消 | MQ 延迟队列消费 |
| 管理端派单 | 分配师傅 |
| 师傅接单 / 拒单 | 拒单则重新派单 |
| 开始服务 / 完成服务 | 状态推进 |
| 到店核销 | 用核销码验证 |
| 各状态订单数量统计 | 管理端工作台用 |

### 模块 6 · 评价

**职责**：评价提交、展示、回复、评分回写。

| 做什么 | 说明 |
|---|---|
| 提交评价（三维打分 + 图文） | 唯一索引防重复 |
| **评分异步回写** | MQ 异步更新师傅和服务项目的评分 |
| 服务详情页展示评价 | 分页 + 按评分筛选 |
| 管理端评价管理（隐藏/回复） | 运营介入 |
| **7 天未评价自动好评** | MQ 延迟队列 |

### 模块 7 · 地址与区域

**职责**：地址簿管理、服务范围校验。

| 做什么 | 说明 |
|---|---|

| **服务范围校验** | 下单时用 district_code 匹配 service_area |
| **经纬度存储** | 为就近派单做准备 |

### 模块 8 · 统计报表

**职责**：把订单、用户、服务的流水数据汇总成运营能看懂的报表。

原项目这块的代码在外卖代码清理时被一并删掉了（它查的是 `orders` 表），
现在按 `service_order` 重新实现了一整套。

| 接口 | 说明 |
|---|---|
| `GET /admin/report/overview` | 经营概览，工作台首屏用：今日营业额/单量/新增用户 + 各状态订单数 + 平台资源数 + 近 7 天趋势 |
| `GET /admin/report/turnoverStatistics` | 营业额统计（按天） |
| `GET /admin/report/userStatistics` | 用户统计（每日新增 + 累计） |
| `GET /admin/report/ordersStatistics` | 订单统计（总量、有效量、完成率） |
| `GET /admin/report/top10` | 服务销量 Top10 |
| `GET /admin/report/export` | 导出 Excel 运营报表（POI） |

**统一的统计口径（全平台只有这一套定义，写在 `ReportMapper.xml` 顶部）：**

| 指标 | 口径 |
|---|---|
| 营业额 | 已付款 **且** 服务已完成（状态 5 待评价 / 6 已完成），按 `checkout_time`（支付时间）归集 |
| 有效订单 | 状态 5 或 6 的订单 |
| 订单完成率 | 有效订单数 ÷ 订单总数 |
| 销量 | 已完成订单的明细数量按服务名汇总 |

两个容易被问到的取舍：

1. **营业额为什么按支付时间而不是下单时间**：下单不等于收到钱，
   用户 23:58 下单、次日 00:01 付款，按下单日算会让报表和实际到账对不上。
2. **为什么按明细表里的服务名聚合销量**：服务项目可能改名甚至下架，
   按 `service_id` 关联会漏掉历史数据，而订单明细里的名字是下单当时的快照。

**补零**：`group by` 只会返回「有数据的那几天」，直接丢给前端画折线图，
日期和数值就会错位。服务层统一按日期区间补齐并补 0，保证两个数组严格等长。

### 模块 9 · 基础设施

**职责**：不属于任何业务，但所有业务都要用。技术亮点的集中地。

| 做什么 | 说明 |
|---|---|
| Redis 缓存 | 服务列表、分类、服务详情的缓存与失效 |
| Redis 分布式锁 | 定时任务多实例互斥（Redisson，见亮点 4 下方的说明） |
| Redis 限流 | `@RateLimit` 注解 + AOP |
| MQ 延迟队列 | 四类延迟业务的统一实现 |
| MQ 消息可靠性 | 生产者确认、手动 ACK、幂等消费 |
| WebSocket 推送 | 新订单来单提醒 + 服务前提醒，实时推给管理端 |
| 定时对账 | 兜底修正 Redis 与 MySQL 不一致 |

## 三、核心业务流程

### 流程 1 · 浏览与下单（主流程）

```
小程序首页
   │  GET /user/category/list           加载服务分类
   │  GET /user/service/list?categoryId 加载服务列表（走 Redis 缓存）
   ▼
服务详情页
   │  GET /user/service/{id}            服务详情 + 规格 + 评价
   │  GET /user/slot/available          查该服务某天的可预约时段
   ▼
加入服务清单
   │  POST /user/shoppingCart/add       选规格（带价差）
   ▼
提交订单
   │  ① 校验服务区域（district_code 是否在 service_area）
   │  ② 校验时段有效性
   │  ③ 【Redis】Lua 脚本原子预扣名额  ← 核心
   │  ④ 落库：service_order + service_order_item
   │  ⑤ 【MQ】发 15 分钟延迟消息        ← 核心
   ▼
微信支付
   │  PUT /user/order/payment
   ▼
支付回调 /user/notify/paySuccess
   │  ① 分布式锁 + 订单号唯一索引保证幂等
   │  ② 【MySQL】乐观锁扣减 booked_count
   │  ③ 订单状态 → 待接单
   │  ④ 【MQ】发服务前 1 小时提醒消息
   ▼
等待派单
```

### 流程 2 · 派单与服务

```
管理端看到「待接单」订单
   │  PUT /admin/order/dispatch   派单
   │  派单算法：技能过滤 → 状态过滤 → 档期过滤 → 评分排序
   ▼
【MQ】发 5 分钟接单超时消息
   │
   ├── 师傅接单 PUT /provider/order/accept
   │      │  订单状态 → 已接单
   │      │  WebSocket 推送给管理端
   │      │  【MQ】服务前 1 小时提醒用户和师傅
   │      ▼
   │   师傅上门 → 开始服务 → 订单状态 → 服务中
   │      ▼
   │   服务完成 → 订单状态 → 待评价
   │      │  【MQ】发 7 天自动好评消息
   │      │  更新师傅 order_count
   │      ▼
   │   用户评价 → 订单状态 → 已完成
   │
   └── 5 分钟未接单
          │  自动转派给下一个师傅（回到派单步骤）
```

### 流程 3 · 订单超时取消（MQ 延迟队列主场景）

```
提交订单时
   └── 发消息到 life.order.delay.exchange
          │
          ▼
      life.order.delay.queue（没有消费者，消息在这里干等 15 分钟）
          │
          │ TTL 到期，成为死信
          ▼
      life.order.dlx.exchange
          │
          ▼
      life.order.timeout.queue
          │
          ▼
      OrderTimeoutConsumer 消费
          │
          ├─ 幂等检查：先查订单，只有仍为「待付款」才继续
          │   （RabbitMQ 是至少一次投递，消息可能重复到达）
          │
          ├─ 已支付 → 直接跳过
          │
          └─ 仍待付款
                 ├── 订单状态 → 已取消，原因「超时未支付」
                 ├── 【Redis】Lua 脚本回补名额（幂等）
                 └── WebSocket 通知管理端
```

**这套设计替代了原项目的 `OrderTask.processTimeoutOrder()`**，
对比一下差别就明白为什么值得改：

| | 原定时任务方案 | MQ 延迟队列方案 |
|---|---|---|
| 触发精度 | 最坏差 1 分钟（每分钟扫一次） | 精确到毫秒 |
| 数据库压力 | 每分钟一次全表扫描，订单越多越慢 | 零空转，只在有订单时产生负载 |
| 失败处理 | 只能等下一轮扫描 | 失败自动重试 3 次 |
| 扩展性 | 多实例部署会重复执行（需要分布式锁） | 天然支持多实例竞争消费 |

**但 `OrderTask` 不要删**，把它降级成兜底对账任务。
理由是 MQ 不是 100% 可靠——可能丢消息、消费者可能挂、
Redis 可能挂了之后重启丢数据。保留定时对账是工程上负责任的做法，
答辩时主动说出这一点，比只说「我用了 MQ」有说服力得多。

### 流程 4 · 评价与评分回写

```
订单状态 → 待评价
   │
   ├── 用户提交评价
   │      │  三维打分 + 图文
   │      │  【MQ】异步回写评分
   │      ▼
   │   ReviewConsumer 消费
   │      ├── 更新 provider.score / good_rate
   │   └── 更新 service_item.score
   │      │
   │      ▼
   │   订单状态 → 已完成
   │
   └── 7 天未评价（MQ 延迟队列触发）
          │  自动标记已完成，默认好评
          └─ 避免订单永远挂在「待评价」，统计口径才好算
```

### 流程 5 · 兜底对账

```
OrderTask（每 5 分钟）
   │
   ├── 1. 扫 Redis 与 MySQL 的名额差异
   │      对每个 slot：Redis 剩余 + 已预约数  vs  total_stock - booked_count
   │      不一致 → 以 MySQL 为准，重写 Redis
   │
   ├── 2. 扫「待付款但已超过 20 分钟」的订单
   │      （兜底 MQ 丢消息的情况）
   │      → 关单 + 回补名额
   │
   └── 3. 扫「待评价超过 7 天」的订单
          → 自动完成
```

## 四、技术亮点设计

### 亮点 1 · Redis 原子预扣防超卖

**问题**：周末 9:00-11:00 的深度保洁只有 3 个师傅能接。
100 个人同时抢，如果用数据库行锁，请求会串行化，吞吐上不去；
如果先查再扣，两步之间有竞态窗口，必然超卖。

**方案**：把「校验名额 → 扣减 → 记录用户」三步写进一个 Lua 脚本。
Redis 单线程执行脚本，期间不会插入其他命令，天然原子。

脚本见 `sky-server/src/main/resources/lua/slot_deduct.lua`，
返回值约定：`>=0` 成功、`-1` 未预热、`-2` 已约满、`-3` 重复预约。

**关键细节**：执行 Lua 必须用 `StringRedisTemplate`。
如果用了配 JSON 序列化器的 `RedisTemplate`，Lua 里 `tonumber()`
拿到的会是带引号的字符串，直接报错。这个坑很多人踩。

**名额回补的幂等**：`slot_rollback.lua` 用 `SREM` 的返回值做判断——
返回 1 说明确实移除了（第一次回补），返回 0 说明已经回补过。
没有这道判断的话，订单取消接口被重复调用会把名额越加越多。

### 亮点 2 · Redis 与 MySQL 双层库存 + 定时对账

单靠 Redis 不安全（Redis 可能挂、可能丢数据），
单靠 MySQL 性能不够。所以做成两层：

| 时机 | 操作 |
|---|---|
| 下单 | Redis 预扣（快，抗并发） |
| 支付成功 | MySQL 乐观锁落账（准，作最终事实） |
| 取消 / 超时 | Redis 回补 + MySQL 释放 |
| 每 5 分钟 | 定时对账，以 MySQL 为准修正 Redis |

这就是 CAP 里的最终一致性实践，也是答辩能讲深度的点。

### 亮点 3 · MQ 延迟队列的四种业务落地

同一套 TTL + 死信队列机制，复用在四个场景：

| 场景 | 延迟 | 类型 |
|---|---|---|
| 订单超时取消 | 15 分钟 | 固定延迟 |
| 服务前 1 小时提醒 | 视预约时间而定 | 不定延迟 |
| 完成后 7 天自动好评 | 7 天 | 固定延迟 |
| 派单后 5 分钟未接单转派 | 5 分钟 | 固定延迟 |

**TTL 队列化实现要点**：声明一个没有消费者的队列，
消息在里面等 TTL 到期变成死信，被死信交换机转发到真正被监听的队列。

**要主动说明的已知问题**：不定延迟场景会有「队头阻塞」——
队列里的消息是先进先出排队过期的，只有队头过期了才会检查下一条。
如果队头是一条 TTL 23 小时的消息，后面 TTL 1 小时的消息也得等。
解决方案是装 `rabbitmq_delayed_message_exchange` 插件（内部用时间轮），
或拆成多个固定档位的队列。

**消息可靠性三件套**：

1. 生产者确认（`publisher-confirm-type: correlated`）—— 消息没到交换机时能感知
2. 生产者退回（`publisher-returns: true`）—— 路由不到队列时能感知
3. 消费者手动 ACK（`acknowledge-mode: manual`）—— 处理成功才确认

### 亮点 4 · 缓存三兄弟

原项目除了一个 `SHOP_STATUS` 之外几乎没用缓存。补上之后：

| 问题 | 场景 | 方案 |
|---|---|---|
| 穿透 | 有人拿不存在的服务 id 反复请求 | 查不到也缓存（空值占位，TTL 60 秒） |
| 击穿 | 热门服务缓存刚好过期，瞬间大量请求打到数据库 | SETNX 互斥锁重建，只放一个请求去查库 |
| 雪崩 | 大批服务缓存设置了相同的过期时间，同时失效 | 随机 TTL（基础值 + 0~20% 随机偏移） |

落地位置：`CacheHelper` 统一实现这三种保护，作用于
分类列表、按分类的服务列表、服务详情三个读接口；
管理端增删改服务项目 / 分类时按前缀整体清除相关缓存。

三个有意的取舍（答辩常被追问，先写在文档里）：

1. **为什么没用布隆过滤器**：本项目服务项目只有几十个、id 自增，
   空值缓存已经能挡住穿透；而布隆过滤器还要额外维护预热和删除
   （服务下架得从过滤器里移除），在小 id 场景收益不划算。
2. **为什么是删缓存而不是更新缓存**：并发写时「更新缓存」容易出现
   后写的先到、缓存里留下旧值；删除是幂等的，下次未命中自然回填最新数据。
3. **为什么分布式锁没用在「防重复下单」上**：下单的重复提交已经被
   Redis Lua 的「一人一时段一单」和 MySQL 状态 CAS 两层挡住，
   再加锁只是多一个故障点。Redisson 真正的落点是下面的定时任务。

**分布式锁的实际用途**：`@Scheduled` 在**每个实例**上都会跑，
多实例部署时两个实例会同时扫同一批超时订单、跑同一轮库存对账。
`ServiceOrderTask` 用 Redisson 的 `RLock.tryLock` 保证同一时刻只有一个实例执行，
拿不到锁的直接跳过。

### 亮点 5 · 限流与防刷

`@RateLimit` 注解 + AOP 切面，用 Redis 计数器（INCR + EXPIRE）实现：

| 接口 | 限制（同一用户） |
|---|---|
| 提交订单 | 10 秒内最多 3 次 |
| 订单支付 | 10 秒内最多 5 次 |
| 提交评价 | 10 秒内最多 3 次 |

两个设计点：

1. **按用户维度而不是 IP**：校园网 / 公司网出口 IP 共用，
   按 IP 限流会误伤同一栋楼的所有人；限流本来就是防单个账号连点。
   未登录场景（本项目写接口都要求登录）才退化成按 IP。
2. **只在第一次自增时设置过期时间**：每次请求都 `EXPIRE` 的话，
   用户一直点就会一直续期，窗口永不失效，限流变成「永不恢复」。

### 亮点 6 · 订单状态实时推送

复用原项目已有的 WebSocket（`/ws/{sid}`），新增 `AdminNotifier` 统一拼装消息：

| 时机 | 推送内容 |
|---|---|
| 订单支付成功进入待接单 | `{type:1, orderId, content}` → 管理端弹窗 + 提示音，点击跳派单中心 |
| 服务前 1 小时（由 MQ 延迟消息触发） | `{type:2, orderId, content}` → 提醒运营通知师傅出发 |

前端按 `type` 决定提示音和文案；推送失败只记日志，不影响支付主流程。
