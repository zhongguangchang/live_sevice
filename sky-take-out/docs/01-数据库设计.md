# 生活服务网 · 数据库设计

数据库名 `life_service`，共 **16 张表**，按 7 个业务域划分。
建表脚本见 `db/life_service.sql`（可重复执行，含初始化数据）。

所有表统一预留 `merchant_id`（默认 1）。单商户阶段它没有实际作用，
但有了它，将来升级成「多商户入驻平台」时不用改表结构、不用数据迁移。

---

## 域一 · 用户与权限

生活服务有「两类完全不同的账号」：一类是坐办公室用后台的运营人员，
一类是上门干活的师傅。它们的工作方式、权限、结算方式都不一样，
所以必须拆成两张表，不能像原项目那样都塞进 `employee`。

### 1. `employee` 平台员工表

管理后台的登录账号。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | BIGINT | 主键 |
| username | VARCHAR(32) | 登录用户名，唯一 |
| name | VARCHAR(32) | 姓名 |
| password | VARCHAR(64) | MD5 加密存储 |
| phone | VARCHAR(11) | 手机号 |
| sex | VARCHAR(2) | 性别 0女 1男 |
| id_number | VARCHAR(18) | 身份证号 |
| **role** | TINYINT | **新增**。角色 1超级管理员 2运营 3派单员 |
| status | INT | 账号状态 0锁定 1正常 |
| create_time / update_time | DATETIME | 创建 / 更新时间 |
| create_user / update_user | BIGINT | 创建人 / 修改人 id |

**为什么加 role**：原项目所有员工权限一样，谁都能改任何东西。
生活服务网的业务链条更长，需要区分职责——运营只管服务项目上架，
派单员只管订单分配，超管才能建账号。

### 2. `user` 用户表

小程序端下单的用户。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | BIGINT | 主键 |
| openid | VARCHAR(45) | 微信用户唯一标识，唯一索引 |
| **unionid** | VARCHAR(45) | **新增**。微信开放平台标识，将来做 App 多端打通用 |
| name / phone / sex / id_number | — | 基本信息 |
| avatar | VARCHAR(500) | 头像 url |
| **status** | TINYINT | **新增**。0禁用 1正常，用于封禁恶意用户 |
| create_time | DATETIME | 注册时间 |
| **last_login_time** | DATETIME | **新增**。用于统计活跃用户 |

## 域二 · 服务商品

这是最核心的改造区。原项目卖的是「菜品 / 套餐」，新项目卖的是
「服务项目 / 服务套餐」。看着只是换个词，但有几个本质差异：

1. 外卖的价格是固定的；生活服务按面积、匹数、时长浮动，所以规格要能带价差
2. 外卖没有时间概念；生活服务必须知道「做一次要多久」，才能排期
3. 外卖只能送上门；生活服务分上门和到店两种，流程完全不同

### 3. `category` 服务分类表

对应小程序首页的分类导航。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | BIGINT | 主键 |
| type | INT | 1服务项目分类 2服务套餐分类 |
| name | VARCHAR(32) | 分类名称，唯一 |
| **icon** | VARCHAR(500) | **新增**。分类图标，小程序首页金刚区要显示图片 |
| sort | INT | 排序，数字越小越靠前 |
| status | INT | 0禁用 1启用 |
| create_time 等 | — | 审计字段 |

初始数据：家政保洁、家电维修、搬家运输、美容美发、开锁换锁、管道疏通、跑腿代办、宠物服务。

### 4. `service_item` 服务项目表 ★核心

平台售卖的最小服务单元，替代原 `dish` 表。

| 字段 | 类型 | 说明 |
|---|---|---|
| id / name / category_id | — | 主键、服务名、所属分类 |
| price | DECIMAL(10,2) | 服务价格 |
| **original_price** | DECIMAL(10,2) | **新增**。划线价，用于展示「原价 199 现价 149」 |
| image / description | — | 图片、描述 |
| **detail** | TEXT | **新增**。富文本详情，写清楚服务包含什么、不包含什么、注意事项。这块在生活服务里极其重要，因为纠纷大多来自「以为包含但实际不包含」 |
| **unit** | VARCHAR(16) | **新增**。计价单位：次/小时/平方米/台 |
| **duration** | INT | **新增**。服务时长（分钟）。排期系统的基石——师傅 9 点开始做一个 120 分钟的单，那 11 点前他都没空 |
| **service_mode** | TINYINT | **新增**。1上门 2到店 3都支持 |
| **need_appoint** | TINYINT | **新增**。是否需要预约。跑腿代办这类可能随叫随到，不需要选时段 |
| **sales** | INT | **新增**。累计销量（冗余） |
| **score** | DECIMAL(3,2) | **新增**。综合评分（冗余），由评价模块回写 |
| status | INT | 0停售 1起售 |

**关于冗余字段的取舍**：`sales` 和 `score` 严格来说是冗余的，可以从
订单表和评价表算出来。但服务列表页要按销量排序、要显示评分，
每次 `count(*)` 全表扫订单表代价太大。这里用空间换时间，
由订单完成和评价提交时异步回写。

### 5. `service_spec` 服务规格表

替代原 `dish_flavor` 口味表。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | BIGINT | 主键 |
| service_id | BIGINT | 所属服务项目 |
| name | VARCHAR(32) | 规格名，如「房屋面积」 |
| value | VARCHAR(64) | 规格值，如「60-90平方米」 |
| **price_delta** | DECIMAL(10,2) | **新增**。加价金额 |
| **sort** | INT | **新增**。同规格下排序 |

**为什么必须有 price_delta**：外卖的「微辣/中辣/特辣」不影响价格，
所以原项目的 `dish_flavor` 只有 name 和 value 两个字段就够了。
但生活服务不一样——100 平米的房子保洁就是要比 60 平米的贵，
规格必须能表达价差。

### 6. `service_package` 服务套餐表

替代原 `setmeal` 表。把多个服务打包优惠卖。

| 字段 | 类型 | 说明 |
|---|---|---|
| id / category_id / name | — | 主键、分类、套餐名 |
| price | DECIMAL(10,2) | 套餐价 |
| **original_price** | DECIMAL(10,2) | **新增**。各项单买之和，用于展示优惠力度 |
| image / description | — | 图片、描述 |
| **duration** | INT | **新增**。套餐总时长，排期要用 |
| **service_mode** | TINYINT | **新增**。服务方式 |
| **sales** | INT | **新增**。累计销量 |
| status | INT | 0停用 1启用 |

例如「新居开荒保洁套餐 = 深度保洁 + 玻璃清洗 + 甲醛检测」，
单买 468，套餐 399。

### 7. `service_package_item` 套餐明细表

替代原 `setmeal_dish` 表。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | BIGINT | 主键 |
| service_package_id | BIGINT | 套餐 id |
| service_id | BIGINT | 服务项目 id |
| name | VARCHAR(64) | 服务名称（冗余快照） |
| price | DECIMAL(10,2) | 服务单价（冗余快照） |
| copies | INT | 份数 |

**冗余 name 和 price 的原因**：套餐卖出去之后，运营可能会给某个服务改名
或调价。如果套餐明细只存 id，历史套餐的展示内容就会跟着变，
用户看到的内容和当初买的不一致。存快照就没这个问题。

## 域三 · 服务人员

### 8. `provider` 服务人员表 ★核心新增

师傅档案。这是原项目完全没有的概念。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | BIGINT | 主键 |
| **employee_id** | BIGINT | 关联的后台账号 id。可以为空——师傅不一定有后台账号 |
| **openid** | VARCHAR(45) | 师傅端小程序的微信 openid |
| name / phone / avatar / sex / id_number | — | 基本信息，手机号唯一 |
| **cert_image** | VARCHAR(500) | 资质证书图。健康证、电工证、高空作业证。上门服务进用户家门，这个是合规刚需 |
| **work_years** | INT | 从业年限，展示给用户增加信任 |
| **intro** | VARCHAR(500) | 个人简介 |
| **service_mode** | TINYINT | 能提供的服务方式 1上门 2到店 3都支持 |
| **status** | TINYINT | **1可接单 2忙碌 3休息中 4已离职**。派单时只筛 1 |
| **score** | DECIMAL(3,2) | 综合评分，评价模块回写 |
| **good_rate** | DECIMAL(5,2) | 好评率百分比，评价模块回写 |
| **order_count** | INT | 累计完成订单数 |

**为什么 score / good_rate / order_count 要单独存在师傅身上**：
派单需要按「评分高、当前负担轻」排序。如果每次都去评价表
`avg(score) group by provider_id` 现算，师傅一多就是性能灾难。

### 9. `provider_skill` 服务人员技能表 ★新增

师傅会干什么，多对多。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | BIGINT | 主键 |
| provider_id | BIGINT | 服务人员 id |
| category_id | BIGINT | 擅长的服务分类 id |
| **level** | TINYINT | 技能等级 1初级 2中级 3高级，影响派单优先级 |

唯一索引 `(provider_id, category_id)` 防止重复配置。

**作用**：派单的第一层过滤。一个空调维修的单，只应该派给
技能里包含「家电维修」分类的师傅，而不是把全平台师傅都拉出来算一遍。
这是把 O(n) 的派单计算降成 O(小集合) 的关键。

## 域四 · 排期与时段

### 10. `slot` 服务时段排期表 ★核心新增

Redis 并发亮点的数据库依据。

| 字段 | 类型 | 说明 |
|---|---|---|
| id | BIGINT | 主键 |
| provider_id | BIGINT | 服务人员 id |
| service_id | BIGINT | 服务项目 id |
| service_date | DATE | 服务日期 |
| start_time / end_time | TIME | 时段起止 |
| **total_stock** | INT | 该时段总名额 |
| **booked_count** | INT | 已预约数量（含已下单未支付的占用） |
| status | TINYINT | 1可预约 0已关闭 |
| **version** | INT | 乐观锁版本号 |

唯一索引 `(provider_id, service_date, start_time)` 防止重复生成时段。

**一行代表什么**：张师傅 2026-09-20 09:00-11:00 做深度保洁，1 个名额。

**库存双层结构**（本项目最重要的设计）：

| 层 | 位置 | 作用 | 用什么保证 |
|---|---|---|---|
| 预扣层 | Redis `slot:stock:{slotId}` | 承接并发抢购，完全不碰数据库 | Lua 脚本原子性 |
| 权威层 | MySQL `total_stock` / `booked_count` | 真正落账，作为最终事实 | 乐观锁 `where booked_count < total_stock` |
| 兜底层 | 定时任务 | 修正两层不一致 | 每 5 分钟对账 |

## 域五 · 交易

### 11. `shopping_cart` 服务清单表

替代原购物车。原项目 1:1 换字段名即可。

| 字段 | 说明 |
|---|---|
| id / user_id | 主键、用户 |
| name / image | 服务名称、图片（冗余快照） |
| service_id | 服务项目 id（与套餐 id 二选一） |
| service_package_id | 服务套餐 id |
| **spec** | **改**。原 `dish_flavor` 是纯文本，现在存 JSON，如 `{"房屋面积":"60-90平方米"}`，因为要参与价格计算 |
| number / amount | 数量、金额（含规格加价后的实际单价） |
| create_time | 创建时间 |

严格说生活服务不该叫「购物车」，叫「待预约清单」更贴切，
但为了跟前端路由保持一致，表名先沿用。

### 12. `service_order` 服务订单表 ★核心

替代原 `orders` 表。这是改动最大的一张表。

**删掉的字段**（都是外卖配送专属）：
`delivery_status`（是否立即送出）、`estimated_delivery_time`（预计送达）、
`delivery_time`（送达时间）、`pack_amount`（打包费）、
`tableware_number` / `tableware_status`（餐具数量）。

**保留的字段**：id、number、status、user_id、amount、pay_method、
pay_status、order_time、checkout_time、user_name、consignee、
phone、address、remark、cancel_reason、cancel_time。

**新增的字段**：

| 字段 | 类型 | 说明 |
|---|---|---|
| **provider_id** | BIGINT | 指派的服务人员，派单后回填 |
| **slot_id** | BIGINT | 预约的时段 id |
| **service_mode** | TINYINT | 1上门 2到店 |
| **service_time** | DATETIME | 预约上门/到店的具体时间 |
| **service_duration** | INT | 预计服务时长（分钟） |
| **verify_code** | VARCHAR(16) | 到店核销码（6位数字） |
| **verify_time** | DATETIME | 核销时间 |
| **dispatch_time** | DATETIME | 派单时间 |
| **accept_time** | DATETIME | 师傅接单时间 |
| **start_time** | DATETIME | 开始服务时间 |
| **finish_time** | DATETIME | 服务完成时间 |
| **rejection_reason** | VARCHAR(255) | 师傅拒单原因 |

**状态设计**（从原项目的 6 个状态扩展到 7 个）：

| 值 | 状态 | 说明 |
|---|---|---|
| 1 | 待付款 | 下单后，等待支付 |
| 2 | 待接单 | 已支付，等待派单 / 师傅接单 |
| 3 | 已接单 | 师傅已接，等待上门或到店 |
| 4 | 服务中 | 师傅已开始服务 |
| 5 | **待评价** | 服务完成。原项目直接跳到「已完成」，这里拆成两步 |
| 6 | 已完成 | 用户评价完成，或 7 天未评价自动完成 |
| 7 | 已取消 | 超时未支付、用户取消、师傅拒单 |

**为什么「已完成」要拆成两步**：生活服务的闭环是「服务做完 +
用户评价」。服务做完就标记完成的话，评价就失去触发时机了，
而且统计数据里分不清「服务好所以及时评价」和「服务差所以拖着不评」。

**唯一索引 `uk_number`**：订单号唯一约束是幂等方案的最后一道防线，
即使分布式锁失效、消息重复消费，数据库这一层也拦得住重复订单。

### 13. `service_order_item` 订单明细表

替代原 `order_detail` 表。name / spec / price / image 全部是下单瞬间快照。

| 字段 | 说明 |
|---|---|
| id / order_id | 主键、订单 id |
| service_id / service_package_id | 服务项目 / 套餐 id |
| name / spec / price / image | 名称、规格、单价、图片快照 |
| number / amount | 数量、小计 |
| **duration** | **新增**。单项服务时长（分钟） |

### 14. `address_book` 服务地址表

沿用原结构，只加一个字段。

| 新增字段 | 说明 |
|---|---|
| **location** | VARCHAR(64)，经纬度如 `116.404,39.915`。两个用途：① 下单时校验地址是否落在服务范围内 ② 派单时按距离就近分配师傅 |

## 域六 · 评价

### 15. `review` 评价表 ★核心新增

| 字段 | 类型 | 说明 |
|---|---|---|
| id | BIGINT | 主键 |
| **order_id** | BIGINT | 订单 id，**唯一索引**，保证一单只能评一次 |
| user_id | BIGINT | 评价人 |
| provider_id | BIGINT | 被评价的师傅 |
| service_id | BIGINT | 被评价的服务项目 |
| **score** | TINYINT | 综合评分 1-5 |
| **service_score** | TINYINT | 服务态度 1-5 |
| **speed_score** | TINYINT | 响应速度 1-5 |
| **quality_score** | TINYINT | 服务质量 1-5 |
| content / images | — | 文字内容、图片（多个逗号分隔） |
| **is_anonymous** | TINYINT | 是否匿名 |
| reply / reply_time | — | 平台/商家回复及时间 |
| status | TINYINT | 0隐藏 1显示，运营可以下架恶意评价 |
| create_time | DATETIME | 评价时间 |

**为什么要拆三个维度打分**：只给一个总分的话，「师傅态度很好但堵车
来晚了」和「来得很快但活干得糙」都是 3 分，平台完全不知道问题出在哪。
拆开之后，`speed_score` 低说明调度有问题，`quality_score` 低说明
培训或考核有问题，`service_score` 低说明人的问题。

**评价提交后要异步回写三处**（这是 MQ 的用武之地）：

1. `provider.score` / `provider.good_rate` —— 影响下次派单优先级
2. `service_item.score` —— 影响列表页展示
3. 订单状态从「待评价」推进到「已完成」

## 域七 · 服务区域

### 16. `service_area` 服务区域表 ★新增

| 字段 | 类型 | 说明 |
|---|---|---|
| id | BIGINT | 主键 |
| name | VARCHAR(32) | 区域名，如「海淀区」 |
| code | VARCHAR(12) | 区级区划编号，唯一 |
| city_code / city_name | — | 所属市 |
| sort | INT | 排序 |
| status | TINYINT | 0未开通 1已开通 |

**作用**：平台不是哪儿都上门。用户下单时拿地址的 `district_code`
匹配这张表，匹配不到就提示「该区域暂未开通服务」。
这是生活服务网比外卖多出来的一道业务校验——外卖只要商家在配送范围内就行，
生活服务得先保证有师傅能到。
